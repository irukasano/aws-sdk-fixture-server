# Lessons

- PR workflow の `テスト` 節は実行コマンドだけで済ませず、各コマンドが証明する観点（例: JWT 署名/JWKS、default fallback、SDK deserialization）を併記する。Skill の「tested perspectives and commands」を満たすことを作成前に確認する。

## 2026-09-07

- HLD を根拠に仕様確認する際は、途中の節で確認を打ち切らず、文書末尾まで読み、明示された実装言語・受け入れ条件・実装順を確認してから未確定事項と判断する。
- HLD のテスト要件を確認する際は、列挙された最低限の対象を省略せず、質問や計画には全対象（本件では JavaScript / TypeScript と Python）を反映する。
- HLD が `defaults/*.yml` のように構成と責務を明示している場合、別方式を推奨する前に当該記述との整合を確認する。
- 外部プロトコルの対応可否を問題として提示する前に、対象 SDK・対象バージョンでの現行仕様を一次情報で確認する。本件の SQS は JavaScript / TypeScript と Python の SDK で AWS JSON protocol を使用できるため、HLD の `aws-json-1.0` 対応で初期要件を満たす。
- 仕様確認では「generic」などの曖昧な外来語を使わず、`AWS_ENDPOINT_URL` のように対象の変数名を明示し、役割を日本語で説明する。
- PR テンプレートでは概要を示す「サマリ」と、レビュー対象の書き漏れを防ぐ「変更範囲」を混在させない。変更範囲は独立した箇条書きセクションにする。
- `docs/ai/tasks/todo/` の見出し日時には、作成・追記時に `date '+%Y-%m-%d %H:%M:%S %Z'` で取得した実時刻を記録する。時刻が不明な過去履歴を推測で修正せず、以後の追記から正確にする。
- PR の `テスト` 欄はテストランナー名やコマンド名を主語にせず、検証した利用者視点の振る舞いを箇条書きにする。実行方法は必要な場合だけ補足する。
- PR 本文の `暫定判断・懸念` には、ユーザーと合意した設計上の暫定判断または利用者に影響する制約だけを記載する。ローカル validator の依存不足のような作業環境上の検証制約は、ユーザー確認なしに PR の懸念として載せない。
- `AI_BASE_DIR/tasks/todo/` のタスク記録は、明示的な除外指示または `.gitignore` がない限り、承認済みタスクの成果物としてコミット対象から独断で除外しない。既存の未追跡ファイルや過去の運用状態だけを除外根拠にしない。
- JWT / JWKS を Fixture として返す設計では、Fixture Server が署名整合性を検証する責務を勝手に追加しない。対応・不整合の検証は利用プログラム側の JWT verifier を用いるテストで扱い、意図的に無効な Fixture を許容する。
- session 固有 URL を JWT の `iss` に含める場合、session 作成前に書かれた固定・事前署名済み JWT は利用できない。Scenario の claim template に session issuer を実行時注入し、固定テスト鍵で署名する stateless な response generation を検討する。
- ユーザーが既存ディレクトリの「改名」を求めた場合、新しい並列ディレクトリを提案して意図を変えない。改名後の責務を既存構成との関係で確認する。
- JWT の `iss` と検証前に必要な issuer 設定を説明するときは、同じ議論を繰り返さず「署名検証の前に信頼する issuer / JWKS URL をアプリへ設定する必要がある」という順序を最初に明示する。
- HTTP request 由来の URL を説明するときは、曖昧な「host」ではなく、値の取得元である HTTP の `Host` ヘッダーを明記する。
